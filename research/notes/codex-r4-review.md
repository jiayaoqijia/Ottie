The most dangerous issue CC missed is control-state poisoning through Ottie’s existing summary path and prompt-epoch drift. The live loop already reloads session summaries on every turn [pkg/agent/loop.go:1039](/home/coder/github/aintern/pkg/agent/loop.go#L1039), injects them into the single system message as privileged `CONTEXT_SUMMARY` text [pkg/agent/context.go:570](/home/coder/github/aintern/pkg/agent/context.go#L570), and rewrites those summaries from model output during compression [pkg/agent/loop.go:1796](/home/coder/github/aintern/pkg/agent/loop.go#L1796). At the same time, the current cache code explicitly rebuilds the system prompt when `MEMORY.md` or any skill file changes [pkg/agent/context.go:195](/home/coder/github/aintern/pkg/agent/context.go#L195), and the tests require that behavior [pkg/agent/context_cache_test.go:129](/home/coder/github/aintern/pkg/agent/context_cache_test.go#L129). That directly contradicts the R3 design’s claimed “frozen prompt until lineage boundary” invariant [research/notes/ottie-learning-loop-design.md:969](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L969). In a crypto agent, one bad summary sentence like “user already authorized future Lido stakes” is enough to bypass the rest of the ACS story.

**A. Crypto-Domain Adversarial Threat Model — REFINE.** Failure scenario: attacker-controlled tool output or skill text gets retained and later influences staking or signing behavior. Reference: Greshake et al. 2023 on indirect prompt injection; Rao & Georgeff 1995 on commitment pathologies. R4 change: add an explicit ACS threat model, provenance bits on every retained artifact, and hard expiry/re-confirm fields on any consent-bearing intention. Priority: `ship before P1`. CC is right on the missing threat model, but “no defense” is too strong: current Ottie already blocks remote exec [pkg/tools/shell.go:194](/home/coder/github/aintern/pkg/tools/shell.go#L194), blocks private-host web fetch [pkg/tools/web.go:982](/home/coder/github/aintern/pkg/tools/web.go#L982), and scans installed skills [pkg/tools/skills_install.go:124](/home/coder/github/aintern/pkg/tools/skills_install.go#L124).

**B. Prompt Injection As First-Class Primitive — REFINE.** Failure scenario: malicious text in `MEMORY.md`, a skill description, or a model-written summary is injected straight into the system prompt [pkg/agent/memory.go:132](/home/coder/github/aintern/pkg/agent/memory.go#L132), [pkg/skills/loader.go:194](/home/coder/github/aintern/pkg/skills/loader.go#L194), [pkg/agent/context.go:570](/home/coder/github/aintern/pkg/agent/context.go#L570). Reference: Greshake et al. 2023. R4 change: provenance and trust labels first, untrusted-context fencing second, dual-model screening only on high-risk write paths, and summaries demoted out of privileged system prose. Priority: `ship before P1`. CC is correct that fences alone are not a boundary. Also, R3’s planned “no mid-session skill rescan” rule [research/notes/ottie-learning-loop-design.md:1007](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1007) is false in the live code and tests [pkg/agent/context_cache_test.go:329](/home/coder/github/aintern/pkg/agent/context_cache_test.go#L329), and `install_skill` currently promises same-session activation [pkg/tools/skills_install.go:195](/home/coder/github/aintern/pkg/tools/skills_install.go#L195).

**C. Cold Start / Bootstrap — REFINE.** Failure scenario: first-session users have no `user_facts`, no intentions, no recall base, and no evaluation baseline, yet the ACS behaves as if those structures already exist. Reference: Rich 1979, *User Modeling via Stereotypes*. R4 change: explicit conservative defaults for first contact, no recall block when empty, first-session elicitation prompts, and “first nightly run becomes baseline” semantics. Priority: `ship before P1`. Current Ottie is mostly empty-safe on memory/session reads [pkg/agent/memory.go:52](/home/coder/github/aintern/pkg/agent/memory.go#L52), [pkg/agent/memory.go:138](/home/coder/github/aintern/pkg/agent/memory.go#L138); the gap is that the R3 design never specifies bootstrap behavior for the new ACS tables and evaluators.

**D. Skill Composition And Interference — REFINE.** Failure scenario: one skill says “auto-stake on APR delta,” another says “always ask before stake,” and Ottie has no explicit arbitration rule. Reference: Erol, Hendler, Nau 1994 on HTN planning. R4 change: effect typing and conflict classes on skills (`reads_state`, `writes_state`, `requires_consent`, `risk_class`) plus runtime impasse handling; not just manually curated `conflicts_with` lists. Priority: `ship before P3`. CC is right that composition theory is missing. The sharper fix is effect semantics, because pairwise compatibility metadata will rot.

**E. Shadow Mode / Simulation Before Production — REFINE.** Failure scenario: a new policy looks safe in logs, but the “shadow” run actually performs live reads/writes against external crypto tools and either doubles side effects or diverges on changing world state. Reference: Sutton 1990, *Integrated Architectures for Learning, Planning, and Reacting*. R4 change: shadow must run on recorded tool fixtures or a replayable tool world, with divergence logs and promotion gates. Priority: `ship before P3`. CC is right on the need for shadowing and wrong that it is cheap. For crypto tooling, “second write path” is not enough.

**F. Reward Hacking Pre-emption — CONFIRM.** Failure scenario: the agent learns to maximize `dry_run`, refusal, or “few tool calls” rather than task completion. Reference: Krakovna et al. 2020; Amodei et al. 2016. R4 change: adversarial reward tests in CI before any reward function is accepted. Priority: `ship before P4`. R3 already exposes hackable proxies in the reward sketch [research/notes/ottie-learning-loop-design.md:929](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L929), so CC is right.

**G. Retrieval-Augmented Hallucination — REFINE.** Failure scenario: Ottie retrieves an old snippet, paraphrases beyond what it supports, and presents it as remembered fact before a crypto action. Reference: Gao et al. 2023; Shuster et al. 2021. R4 change: memory IDs plus a grounding checker on action-relevant claims and consent-relevant facts. Priority: `ship before P1`. Typed case indexing in R3 [research/notes/ottie-learning-loop-design.md:1200](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1200) helps retrieval quality, not grounding. I would not require visible citations in every answer; I would require them at the action boundary.

**H. Economic Feasibility Of The Evaluation Harness — CONFIRM.** Failure scenario: the nightly harness is too expensive, so it gets throttled manually and stops being a trustworthy gate. Reference: Russell & Wefald 1991 on value of computation; Lattimore & Szepesvari 2020 on focused sampling. R4 change: daily smoke, weekly full sweep, monthly adversarial audit, importance sampling on unstable tasks. Priority: `ship before P1`. The design explicitly says nightly CI runs all four suites [research/notes/ottie-learning-loop-design.md:1210](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1210). CC’s cost objection is correct.

**I. Model Drift Vs. Ottie Drift — REFINE.** Failure scenario: a provider change, RPC/API drift, or skill update is misdiagnosed as an Ottie regression. Reference: Kohavi & Longbotham 2017. R4 change: pinned baselines, recorded tool fixtures, variance-aware thresholds, and domain canaries. Priority: `ship before P1`. CC’s direction is right, but `2+2` is a useless canary. Use fixed crypto-domain traces.

**J. Skill Supply-Chain Trust — REFINE.** Failure scenario: a hub-installed skill is compromised or locally modified after install, and its metadata still flows into the prompt path [pkg/skills/loader.go:194](/home/coder/github/aintern/pkg/skills/loader.go#L194). Reference: Thompson 1984, *Reflections on Trusting Trust*. R4 change: commit pinning, content-hash verification on load, TOFU with revocation, diff-reviewed updates, first-run sandbox. Priority: `ship before P3`. CC is directionally right, but the repo is not starting from zero: Ottie already has registry moderation, local scans, and `.skill-origin.json` provenance [pkg/tools/skills_install.go:140](/home/coder/github/aintern/pkg/tools/skills_install.go#L140), [pkg/skills/scan.go:51](/home/coder/github/aintern/pkg/skills/scan.go#L51).

**New Critiques**

1. **Summary poisoning and prompt-epoch drift.** Failure scenario: attacker-controlled text is compressed into session summary, then re-enters future turns as privileged `CONTEXT_SUMMARY` [pkg/agent/context.go:570](/home/coder/github/aintern/pkg/agent/context.go#L570), while memory/skill edits silently trigger prompt rebuilds [pkg/agent/context.go:195](/home/coder/github/aintern/pkg/agent/context.go#L195). Reference: Doyle 1979, *A Truth Maintenance System*. R4 change: introduce `prompt_epoch`, forbid mid-session prompt mutation except explicit lineage breaks, and replace free-form summaries with cited `summary_items` carrying source message IDs and an imperative-strip pass. Priority: `ship before P1`.

2. **No cross-artifact justification graph.** Failure scenario: a jurisdiction or consent fact changes; the related intention, cached case preference, and drafted skill keep firing because contradictions are only local to one table. R3’s Learning Contract lists artifacts independently [research/notes/ottie-learning-loop-design.md:1186](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1186), and the planned `goals`/`user_facts` schemas still have no dependency propagation [research/notes/ottie-learning-loop-design.md:1208](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1208). Reference: Alchourrón, Gärdenfors, Makinson 1985, *On the Logic of Theory Change*. R4 change: add `artifact_evidence` and `artifact_dependencies` tables; when evidence is contradicted, dependent intentions/skills/cases enter `suspended` state until reconciled. Priority: `ship before P3`.

3. **State aliasing under partial observability.** Failure scenario: Ottie retrieves a successful Sepolia dry-run case and reuses it for a mainnet live-wallet situation because the case index knows `chain` and `asset` but not enough execution state. R3’s typed case index stops at `tool`, `chain`, `asset`, `intent`, `outcome`, `failure_mode` [research/notes/ottie-learning-loop-design.md:1200](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1200), while the MDP observation space is still deferred [research/notes/ottie-learning-loop-design.md:1217](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1217). Reference: Kaelbling, Littman, Cassandra 1998, *Planning and Acting in Partially Observable Stochastic Domains*. R4 change: define a versioned `state_signature` now and require retrieval compatibility on fields like `chain_id`, `wallet_mode`, `consent_state`, `tool_health`, and `account_scope`; log the same signature per decision sidecar. Priority: `ship before P1`.

4. **No online metareasoning budget.** Failure scenario: during a fast vault-health event, Ottie spends its latency budget on retrieval checks, scans, nudgers, and shadow logic instead of acting. Reference: Russell & Wefald 1991, *Principles of Metareasoning*. R4 change: every meta-action gets `expected_value`, `expected_latency_ms`, `expected_token_cost`, and `risk_class`; low-risk read-only turns take a cheap path, high-risk turns buy more control computation. Priority: `ship before P3`.
