**Opening**
The most dangerous under-treated issue in R4 is forensic non-reconstructability of side effects. R4 fixed the prompt-epoch lie, but it still leaves Ottie without an end-to-end causal record for a bad signing event. In live code, tool calls execute in parallel [loop.go#L1448](/home/coder/github/aintern/pkg/agent/loop.go#L1448), the loop log omits `tool_call_id` [loop.go#L1466](/home/coder/github/aintern/pkg/agent/loop.go#L1466), registry logs omit `session_key` and causal parentage [registry.go#L237](/home/coder/github/aintern/pkg/tools/registry.go#L237), and persisted session messages have no timestamp field at all [types.go#L65](/home/coder/github/aintern/pkg/providers/protocoltypes/types.go#L65). Worse, side-effecting tools run before any durable pre-call record is written [loop.go#L1516](/home/coder/github/aintern/pkg/agent/loop.go#L1516), [loop.go#L1580](/home/coder/github/aintern/pkg/agent/loop.go#L1580). For a crypto agent, that is the wrong failure mode.

`research/notes/cc-r5-review.md` is not present in this checkout, so the A-J verdicts below are against the agenda in your prompt, grounded in the design doc and live code.

**A-J**
- `A. Observability / incident forensics — CONFIRM.` The planned `sessions/messages` schema has `tool_call_id` but no `trace_id`, `span_id`, or causal clock [ottie-learning-loop-design.md#L140](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L140). R3/R4’s decision sidecar is per-trajectory [ottie-learning-loop-design.md#L1211](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1211); it is not a Dapper-style distributed trace. Add `trace_id`, `span_id`, `parent_span_id`, `lamport`, `decision_id`, `intention_id`, `skill_activation_id`, `memory_read_id`, and `external_action_id` across session open, recall, skill load, tool call, async callback, and summary writeback.

- `B. Mixed-initiative HCI — REFINE.` R4 is still basically binary consent: consent-by-default skill creation [ottie-learning-loop-design.md#L719](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L719), `requires_consent` effect typing [ottie-learning-loop-design.md#L1415](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1415), and a safety/consent regression suite [ottie-learning-loop-design.md#L1218](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1218). What is missing is Horvitz’s expected value of interruption. Ottie needs a turn-level policy with three outputs, not one: `interrupt now`, `act silently`, `defer and summarize later`, parameterized by action reversibility, time pressure, user interruption tolerance, and current uncertainty.

- `C. Confidence calibration — CONFIRM.` The design has a `confidence` notion for user facts [ottie-learning-loop-design.md#L1179](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1179), [ottie-learning-loop-design.md#L1213](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1213), and HELM-style reporting mentions calibration [ottie-learning-loop-design.md#L1219](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1219). But there is no calibration harness, no Brier/ECE target, and no post-hoc calibration procedure. Calibrate separately for fact identification, user-model inference, tool selection, grounding checks, and action safety; one scalar “confidence” is too coarse for crypto.

- `D. Abstention theory — REFINE.` BFCL-Ottie includes abstention in eval [ottie-learning-loop-design.md#L1215](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1215), but runtime policy does not. The live system prompt also pushes against abstention: tool discovery says “Do not refuse a request unless the search returns nothing” [context.go#L150](/home/coder/github/aintern/pkg/agent/context.go#L150). That is incompatible with Chow-style reject options under asymmetric loss. Ottie needs explicit action-boundary outcomes: `ask_user`, `safe_noop`, `defer_for_validation`, `hard_refuse`, with thresholds tied to expected harm, not only tool availability.

- `E. Temporal reasoning / fact staleness — CONFIRM.` R4 gives retrieval decay via activation [ottie-learning-loop-design.md#L1180](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1180), [ottie-learning-loop-design.md#L1204](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1204). That is not temporal truth maintenance. The planned `user_facts` schema only carries `created_at` and `last_used` [ottie-learning-loop-design.md#L1213](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1213). Add `observed_at`, `asserted_at`, `valid_from`, `valid_to`, and query-time `as_of`, with domain volatility classes so APRs, gas, tool health, balances, and contract metadata expire much faster than stable preferences.

- `F. Multi-tenant trust boundaries — CONFIRM.` This is not hypothetical; both the design and live code are single-tenant in important places. The planned recall API omits `user_id` entirely [ottie-learning-loop-design.md#L223](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L223), even though `sessions` stores it [ottie-learning-loop-design.md#L121](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L121). Live code loads workspace-global `USER.md`/`MEMORY.md` into every session [context.go#L177](/home/coder/github/aintern/pkg/agent/context.go#L177), [context.go#L490](/home/coder/github/aintern/pkg/agent/context.go#L490), [memory.go#L132](/home/coder/github/aintern/pkg/agent/memory.go#L132); Telegram group sessions are per room, not per user [telegram.go#L568](/home/coder/github/aintern/pkg/channels/telegram/telegram.go#L568), [session_key.go#L93](/home/coder/github/aintern/pkg/routing/session_key.go#L93). Hermes has already moved to per-user group isolation and user-scoped memory plumbing [sessions.md#L337](/home/coder/github/aintern/research/hermes-agent/website/docs/user-guide/sessions.md#L337), [run_agent.py#L1179](/home/coder/github/aintern/research/hermes-agent/run_agent.py#L1179). Ottie needs mandatory labels on every artifact: `agent_id`, `user_scope`, `account_scope`, `channel_scope`, `peer_scope`.

- `G. Explainability / causal attribution — REFINE.` R4 already has the right raw materials: explicit causal-attribution criterion [ottie-learning-loop-design.md#L1167](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1167) and decision-graph sidecars [ottie-learning-loop-design.md#L1211](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1211). What it lacks is an explanation layer. Miller’s point applies here: users need a compact, contrastive “why this, not that?” explanation, not a raw provenance DAG. Add an explanation compiler that emits `retrieved fact -> intention -> skill -> tool -> external effect`, plus one counterfactual.

- `H. Goodhart corrosion of the eval harness — CONFIRM.` R4 covered reward hacking, economics, and drift, but not harness gaming. Promotion is still framed as beating a frozen baseline [ottie-learning-loop-design.md#L1220](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L1220), which is exactly how teams learn to overfit BFCL/Tau-style suites. Add a hidden rotating slice and a live shadow slice from real production fixtures, then track benchmark-to-production correlation as a first-class metric; when correlation drops, the benchmark is compromised even if the score rises.

- `I. Fail-safe vs fail-operational — REFINE.` I would not say Ottie has no degradation behavior: it already falls back from JSONL to legacy JSON sessions if store init or migration fails [instance.go#L323](/home/coder/github/aintern/pkg/agent/instance.go#L323), and session writes are explicitly fire-and-forget [session_store.go#L10](/home/coder/github/aintern/pkg/session/session_store.go#L10). The problem is that the behavior is implicit and not risk-ranked. Ottie needs an explicit degradation ladder: side-effecting tools fail-safe on storage, telemetry, consent, or principal ambiguity; summarization, search, and recall may fail-operational; eval regressions freeze promotion, not current read-only service.

- `J. Tool-call reliability / Moravec paradox — CONFIRM.` The runtime has almost no measurement of the actual failure modes that dominate production agents. Malformed tool-call JSON is silently coerced into `{}` or `{"raw":...}` [toolcall_utils.go#L62](/home/coder/github/aintern/pkg/providers/toolcall_utils.go#L62), [openai_compat/provider.go#L518](/home/coder/github/aintern/pkg/providers/openai_compat/provider.go#L518), [codex_provider.go#L377](/home/coder/github/aintern/pkg/providers/codex_provider.go#L377), and the registry executes `args map[string]any` without central schema validation [base.go#L5](/home/coder/github/aintern/pkg/tools/base.go#L5), [base.go#L84](/home/coder/github/aintern/pkg/tools/base.go#L84). Add a tool-call validator/telemetry layer before execution and make BFCL-style parameter correctness visible online, not only in offline eval.

**New Critiques**
- `Write-ahead action journal.` Current code persists the tool result only after execution [loop.go#L1516](/home/coder/github/aintern/pkg/agent/loop.go#L1516), [loop.go#L1580](/home/coder/github/aintern/pkg/agent/loop.go#L1580). If a signing RPC or external write succeeds and the process dies before session persistence, the most important fact is lost. R5 needs an outbox-style `action_intents` / `action_commits` ledger with `prepared`, `committed`, `aborted`, args hash, principal scope, and external IDs.

- `Principal-binding / confused deputy.` Routing already knows `account_id`, peer, and sender identity [loop.go#L927](/home/coder/github/aintern/pkg/agent/loop.go#L927), [bus/types.go#L18](/home/coder/github/aintern/pkg/bus/types.go#L18). But tool context only injects `channel` and `chatID` [base.go#L28](/home/coder/github/aintern/pkg/tools/base.go#L28), [registry.go#L255](/home/coder/github/aintern/pkg/tools/registry.go#L255). A future signing or wallet tool therefore cannot verify which principal authorized the call. Add a capability-bearing `PrincipalContext` to every tool invocation.

- `Async completion session collapse.` Async tool callbacks publish inbound `system` messages without the original `SessionKey` [loop.go#L1508](/home/coder/github/aintern/pkg/agent/loop.go#L1508), and `processSystemMessage` routes them into `agent:main:main` [loop.go#L1005](/home/coder/github/aintern/pkg/agent/loop.go#L1005). That breaks privacy, attribution, and any future training data derived from those sessions. This is a concrete code defect, not just a design omission.

- `Replay / execution manifest gap.` The future schema stores `model` and message text [ottie-learning-loop-design.md#L123](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L123), [ottie-learning-loop-design.md#L140](/home/coder/github/aintern/research/notes/ottie-learning-loop-design.md#L140), and the live registry has a mutable version counter [registry.go#L36](/home/coder/github/aintern/pkg/tools/registry.go#L36), [registry.go#L131](/home/coder/github/aintern/pkg/tools/registry.go#L131). But Ottie persists no prompt hash, tool schema hash, skill hash set, MCP server version, or provider request IDs. Hermes at least exposes request-scoped correlation IDs [RELEASE_v0.8.0.md#L253](/home/coder/github/aintern/research/hermes-agent/RELEASE_v0.8.0.md#L253). Ottie needs an `execution_manifest` per turn.

**R5 Deltas**
1. `Ship tenant and principal isolation first.` Add mandatory artifact labels and filters on recall, memory, intentions, skills, and trajectories; fix shared group-session defaults and the async `agent:main:main` collapse.
2. `Add a trace spine.` Persist `trace_id`, `span_id`, `parent_span_id`, Lamport clock, `decision_id`, `intention_id`, `skill_activation_id`, `memory_read_id`, and `external_action_id` across the whole turn.
3. `Add a write-ahead action ledger for side effects.` No signing, broadcast, approval, or funds-moving tool should execute without a durable `prepared` record and a later `commit` or `abort`.
4. `Add calibrated abstention at action boundaries.` Calibrate per action class, then enforce reject/ask/defer thresholds based on asymmetric crypto loss.
5. `Add runtime tool-call validation and telemetry.` Count malformed JSON, schema mismatches, repair attempts, hallucinated tools, missing required params, and retries online.
6. `Add temporal validity semantics.` Introduce `observed_at`, `valid_from`, `valid_to`, and `as_of`; do not let activation decay stand in for truth freshness.
7. `Add an expected-value interruption policy.` Mixed initiative should be a costed choice, not a binary consent gate.
8. `Add hidden/rotating eval slices plus live shadow correlation checks.` Detect benchmark gaming before it becomes organizational folklore.
9. `Add an explanation compiler from the causal graph.` User-facing “why” must be generated from provenance, not from a fresh narrative hallucination.
10. `Add an explicit fail-safe / fail-operational matrix.` Storage, telemetry, principal ambiguity, and eval regressions should each have a defined degradation mode.

The code evidence that most sharply raises the urgency is the combination of workspace-global memory injection, group-session sharing, no principal in tool context, and async result collapse into `agent:main:main`. Those are first-90-day bugs, not long-horizon architecture polish.
